# Task 3 ADR

#### **Название задачи:Открытие депозитов онлайн** 
#### **Автор:Алексей**

### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| - | - | - | - |
| 1. | Клиент| Открытие страницы сайта| Получение актуальной информации о ставках |
| 2. | Клиент| Подача заявки| Ввести свои ФИО и номер телефона для связи |
| 3. | Менеджер кол-центра| Обработка заявки| Предложить условия депозита |
| 4. | Клиент| Идентификация | Визит в отделение и предоставление оригиналов документов |
| 5. | Клиент | Просмотр доступных депозитов | В интернет-банке клиент видит список доступных депозитов с актуальными ставками и персонализированные ставки лично для него |
| 6. | Клиент | Открытие депозита | Указав счёт и сумму депозита, он может подать заявку на открытие депозита. Операцию необходимо будет подтвердить с помощью СМС-кода. |
| 7. | Менеджер бэк офиса | Подтверждение условий депозита  | Обработка открытия депозита. Клиент должен получить СМС-уведомления после подтверждения размера ставки и открытия депозита. |

### **Нефункциональные требования**

|**№**|**Требование**|
| - | - |
| 1. |Функционал работы с СМС реализован в ядре системы. Он требует доработки со стороны подрядчика, но этого лучше избежать. Реализовать такой бизнес-функционал можно силами команды разработки банка |
| 2. | Работу со ставками по депозитам сотрудниками как бэк-офиса депозитов, так и бэк-офиса кредитов стоит реализовать в АБС |
| 3. | Данные при передаче надо защитить каким-то механизмом шифрования |
| 4. | Как можно больше использовать технологии, которые уже есть в банке. БД- MS SQL и Oracle |
| 5. | Для очереди сообщений лучше использовать Kafka |
| 6. | Перевод интернет-банка на микросервисную архитектуру, но пока только в рамках задачи открытия депозитов |
| 7. | Предусмотреть разработку документации для дальнейшего расширения системы |
| 8. | Отклик по всем операциям должен быть максимально быстрым и занимать миллисекунды |
| 9. | Придерживаться системы дизайна для приложений, которая принята в компании. |
| 10. | Все сервисы должны работать 24/7 и быть доступны в 99,9% случаев, поэтому лучше избежать прямой работы интернет-банка с API АБС в новом процессе |
| 11. | В случае сбоев в ЦОД необходимо, чтобы сервисы интернет-банка были доступны и выдерживали требуемую нагрузку |
| 12. | У банка есть резервный ЦОД, в случае сбоя можно переключиться на него |
| 13. | Предусмотреть равномерное горизонтальное масштабирование и распределение запросов между серверами, приложениями и ЦОД |
| 14. | АБС может масштабироваться только вертикально из-за своей базы данных |

### **Альтернативы**

**Недостатки, ограничения, риски**
Использование разнородных систем и языков программирования осложняет развитие и вынуждает держать запасных разработчиков в каждой системе.
Не описан процесс синхронизации  БД между разными ЦОД. Скорее всего тут есть свой VPN обеспечивающий обмен CDC информацией.
АБС без возможности  горизонтального масштабирования станет узким горлышком при росте числа клиентов.
